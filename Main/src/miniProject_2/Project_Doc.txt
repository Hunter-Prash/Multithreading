REAL BACKEND-STYLE MULTITHREADING PROJECT

Goal
Build a small backend-style job processing system that reinforces the multithreading concepts learned in Modules 1–3.

The system will simulate incoming jobs being processed concurrently by a thread pool while multiple workers share a database-like resource. We will introduce concurrency problems and solve them using the appropriate Java concurrency tools.

We will NOT force every concept into the project just for the sake of using it.


PHASE 1 — JOB INGESTION & THREAD POOL
-------------------------------------

What we build:
- Job model representing an incoming job.
- JobProducer that creates jobs.
- Shared BlockingQueue to hold incoming jobs.
- ExecutorService with a fixed-size thread pool.
- Worker tasks that take jobs from the queue and process them.

Flow:

    JobProducer
         |
         v
    BlockingQueue
         |
         v
    ExecutorService
         |
       Workers

How we do it:
1. Create Job objects.
2. Producer places jobs into the BlockingQueue.
3. Worker tasks take jobs from the queue.
4. Multiple workers process jobs concurrently.
5. Use ExecutorService instead of creating a new thread for every job.

Concepts reinforced:
- Runnable
- ExecutorService
- Fixed thread pool
- BlockingQueue
- Concurrent execution


PHASE 2 — SHARED RESOURCE & SYNCHRONIZATION
--------------------------------------------

What we build:
- A shared database-like resource.
- Multiple worker threads access and update it.
- Shared job status/result state.

Flow:

    Worker 1 ----    Worker 2 -----+----> Shared Database
    Worker 3 ----/

How we do it:
1. Multiple workers process jobs simultaneously.
2. Workers access the same database-like resource.
3. Identify operations that must be protected.
4. Use synchronized / ReentrantLock where appropriate.
5. Make the critical section explicit.
6. Observe why shared mutable state can cause race conditions.

Concepts reinforced:
- Shared mutable state
- Race conditions
- synchronized
- ReentrantLock
- Critical sections
- Thread safety


PHASE 3 — CONCURRENCY CONTROL & COORDINATION
--------------------------------------------

What we build:
- AtomicInteger counters for job statistics.
- ConcurrentHashMap for concurrent result storage.
- Semaphore to limit access to the shared database-like resource.
- CountDownLatch for startup/initialization coordination.

Example statistics:

    Total jobs:       100
    Completed:         85
    Failed:             10
    Processing:          5

How we do it:

AtomicInteger:
- Safely maintain counters updated by multiple workers.

ConcurrentHashMap:
- Store job results/status while workers access the map concurrently.

Semaphore:
- Assume only a limited number of database connections/resources exist.
- Example: Semaphore(2) allows at most 2 workers to access the controlled resource.
- Workers acquire a permit before accessing the resource and release it afterward.

CountDownLatch:
- Run required initialization tasks concurrently.
- Main waits at latch.await().
- Each initialization task calls countDown() when its required initialization is complete.
- Processing begins only when the latch reaches zero.

Concepts reinforced:
- AtomicInteger
- ConcurrentHashMap
- BlockingQueue
- Semaphore
- CountDownLatch

PHASE 4 — FAILURE HANDLING, COMPLETION & GRACEFUL SHUTDOWN
-----------------------------------------------------------

What we build:
- Jobs that can succeed or fail.
- Proper cleanup when processing fails.
- Graceful termination of the thread pool.
- Final processing statistics.

Flow:

    Job
     |
     v
    Worker
     |
     +----> SUCCESS
     |
     +----> FAILURE
              |
              v
        update status/statistics
              |
              v
        release resources
              |
              v
        continue processing

How we do it:
1. Workers process jobs inside appropriate try/catch/finally blocks.
2. Failed jobs are recorded instead of crashing the whole processing system.
3. Semaphore permits are released in finally when acquired.
4. Job status and statistics are updated safely.
5. Once all incoming work has been handled, shut down ExecutorService.
6. Use shutdown() and appropriate termination/waiting logic.
7. Verify that all workers have completed before the application exits.

Concepts reinforced:
- Exception handling in concurrent code
- finally for resource cleanup
- Future where useful
- ExecutorService shutdown
- awaitTermination
- Graceful shutdown
- Complete multithreaded workflow
